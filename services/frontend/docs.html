🎯 1. What this project is

This is a DevOps CI/CD training project: a small e-commerce style platform that is deliberately split into a public frontend dashboard plus 12 backend microservices (user, product, order, cart, inventory, payment, notification, review, auth, shipping, search and analytics). Each service is a tiny Node.js / Express app running in its own Docker container.

The application itself is intentionally simple. The real subject of the project is everything around the app: how code goes from a git push all the way to running containers on a server, automatically, through a Jenkins pipeline — with code scanning, image building, a container registry, automated deployment, TLS certificates and monitoring along the way.

💡
One-line summary: the app is the excuse; the pipeline is the lesson. Everything here exists to demonstrate a complete, real-world CI/CD workflow.

🖥 2. How the dashboard webpage works

The dashboard is a plain HTML/CSS/JavaScript page (no framework) served by Nginx from the frontend container. It talks to the backend only through relative /api/* URLs, which Nginx reverse-proxies to the API gateway. Here is what each part does:

  • Deploy strip — shows the build number, domain and service count, fetched from /version on the gateway.
  • System Architecture diagram — a hand-drawn SVG that maps the whole pipeline and the 12-service mesh.
  • Live Service Health — every 8 seconds the page pings each service's /api/health/<service> endpoint, measures latency, and colours the dot green (healthy) or red (unreachable).
  • API Console — the interactive part. When you click a button it fires a real HTTP request through the stack and animates the hop browser → frontend → api-gateway → service and back, logging real status codes and latency. This proves the microservices are actually talking to each other over the Docker network.
  • Data tables & Platform Analytics — live data pulled from the user, product, order, inventory and analytics services.
  • Theme toggle — switches light/dark, remembered in localStorage.

Key point: the browser never contacts the backend services directly. Only the frontend is public (it terminates TLS via nginx-proxy in production); every /api/* call is proxied to the internal api-gateway, which then routes to the right service on the private Docker network.

⚙ 3. Architecture & request flow

A single request from the browser travels like this:

Browser → nginx-proxy (TLS / HTTPS) → frontend (Nginx :80) → api-gateway :8080 → a backend service :3001–:3012

The two build/deploy servers are separated on purpose:

Server A — CI

Runs Jenkins and SonarQube. Builds Docker images, scans code, and pushes images to the registry. Never runs the app itself.

Server B — Deploy

Runs Docker Compose with the app plus nginx-proxy, acme-companion (Let's Encrypt) and the monitoring agents. This is the only box the public reaches.

🚀 4. The DevOps pipeline, stage by stage

A git push fires a GitHub webhook that triggers the Jenkins pipeline defined in Jenkinsfile. It runs these stages in order:

  1. 1

    Checkout

    Jenkins pulls the latest code from the Git repository for this build.

  2. 2

    SonarQube Analysis quality

    Static code analysis scans services/ for bugs, code smells and security issues, and reports them to the SonarQube server.

  3. 3

    Quality Gate gate

    The pipeline waits for SonarQube's verdict. If the code fails the quality gate, the build is aborted — bad code never gets built or deployed.

  4. 4

    Build images build

    docker build runs once per service (14 total), tagging each image with the build number and latest.

  5. 5

    Push images registry

    Jenkins logs in to Docker Hub and pushes every image so the deploy server can pull them later.

  6. 6

    Deploy to server deploy

    Jenkins SSHes into Server B, copies docker-compose.prod.yml, then runs docker compose pull && up -d so the new images go live with zero manual steps.

  7. 7

    Manage demo EC2 (Terraform) infra

    A demo Infrastructure-as-Code stage: Terraform provisions (BUILD) or tears down (DESTROY) an AWS EC2 instance, proving Jenkins can drive infrastructure, not just code.

  8. 8

    Notify notify

    On success or failure, a message with stage timings and instance details is posted to a Google Chat webhook.

🔑
Monitoring (always-on): Prometheus + Loki + Promtail collect metrics and logs on the deploy server, while Grafana runs off-server as a lightweight viewer that queries them over the network.

📁 5. Config files, explained

These are the files that wire everything together. Read this as a map of the repository.

docker-compose.yml

Local development. Builds each service from source and only exposes the frontend on port 8090. Everything else stays on the internal app-net network.

docker-compose.prod.yml

Production. Pulls prebuilt images from the registry instead of building, and adds nginx-proxy + acme-companion for automatic HTTPS via Let's Encrypt.

Jenkinsfile

The CI/CD pipeline as code. Defines every stage from checkout to deploy to Terraform, plus credentials and Google Chat notifications.

services/frontend/nginx.conf

The frontend's Nginx config. Serves the dashboard and reverse-proxies /api/*, /gateway-health, /version, /docs and /api-docs to the gateway.

.env.example

Template for environment variables (REGISTRY, IMAGE_TAG, and in prod DOMAIN / LETSENCRYPT_EMAIL). Copied to .env on the server.

ansible/

Playbooks that automate the two-server setup: install Docker, set up Jenkins, create the deploy user. Uses inventory.ini and vars.yml.

monitoring/

Observability stack config: prometheus.yml, loki-config.yaml, promtail-config.yaml and Grafana provisioning for datasources and dashboards.

scripts/deploy.sh

The manual deploy helper: docker compose pull && up -d. What Jenkins automates in the deploy stage.

services/<name>/Dockerfile

Per-service build recipe: how each microservice's Docker image is assembled from its Node.js source.

📚 6. Glossary of DevOps terms

CI/CD
Continuous Integration / Continuous Deployment — automatically building, testing and shipping code every time it changes.
Pipeline
The ordered set of automated stages (build, test, deploy…) that code passes through, defined here in the Jenkinsfile.
Microservice
A small, independent service that does one job and talks to others over the network, instead of one large monolithic app.
API Gateway
A single entry point that receives all API requests and routes them to the correct backend service.
Container / Image
An image is a packaged, runnable snapshot of a service; a container is a running instance of that image.
Registry
A store for Docker images (here, Docker Hub). Jenkins pushes images to it; the deploy server pulls from it.
Docker Compose
A tool that runs a set of containers together from one YAML file, wiring up their networks and environment.
Webhook
An automatic HTTP callback. GitHub calls Jenkins on every push so the pipeline starts on its own.
Quality Gate
A pass/fail threshold from SonarQube. Failing it stops the pipeline before anything is deployed.
Infrastructure as Code (IaC)
Managing servers and cloud resources through code (Terraform, Ansible) instead of clicking in a console.
Reverse proxy
A server (Nginx) that receives requests and forwards them to internal services, hiding them from the public internet.
TLS / Let's Encrypt
TLS provides HTTPS encryption; Let's Encrypt issues the certificates automatically via acme-companion.
Observability
Seeing inside a running system: metrics (Prometheus), logs (Loki + Promtail) and dashboards (Grafana).
